## A-Q29 — [A] Deleting the kernel's network stack would take container networks with it: rebuild them in the network daemon, and how? — Status: OPEN (raised 2026-10-16)

**In short:** you decided (A-Q9, decision 934) that networking moves out of
the kernel into its own program, the *network daemon*, and that the
kernel's copy is then deleted. The premise was that the daemon does
everything the kernel's copy does. It does not do one thing: container
networks -- the Docker-style networks (decision 60) that let containers
have their own addresses, reach each other, and reach the outside world
through the host. Those still run on the kernel's copy, so deleting it as
decided would remove them. You are asked how they should come back: inside
the one daemon, or as one small network program per container network.

**Terms.** *Network namespace*: a separate copy of the network (its own
addresses, routes and sockets) that a container sees instead of the
host's. *veth*: a virtual cable joining two namespaces. *Bridge*: a
virtual switch joining several veths, so containers on one network reach
each other. *NAT*: rewriting addresses so containers share the host's
connection to the outside.

**Where things stand.** Container networks are reachable only from the
kernel's built-in debugging shell, whose `container`/`oci`/`docker` commands
are the container runtime today; no program can create a container yet.
The rest of the deletion -- the kernel's own name lookups, the native
socket calls, the kernel shell's network commands -- does not depend on
this answer, and lane A goes on with it.

| Option | *What changes:* |
|---|---|
| **A. One daemon serves every network namespace** (as Linux's one kernel stack does) | Container networks come back unchanged to a user: the same `docker network` commands, addresses, same-network reachability and outside access. Inside, the daemon keeps one set of addresses, routes and sockets per namespace, and the veths, bridges and NAT become its own data. |
| B. One small network program per container network | The same commands and behaviour. A container network's traffic is handled by a program of its own, so a fault in one cannot touch the host's networking or another network's; each costs a process and its memory. |
| C. No container networks after the deletion | Containers share the host's network or have none, until a user-space container runtime asks for them again. Decision 60's networks are gone in the meantime. |

- **A** is the smallest step from what exists: the daemon already owns the
  network card and serves everyone's sockets; namespaces become one more key
  in its tables. A fault in the daemon takes every network down at once, as
  a kernel stack fault does on Linux.
- **B** is the more microkernel-shaped design, at the cost of a process per
  network and the plumbing between them (a bridge becomes a channel between
  programs).
- **C** is the quickest, and undoes an answer you gave.
- My recommendation: **A** now. It keeps decision 60's behaviour at the least
  cost, and nothing in it rules out moving to B later.

**If it is never answered:** nothing breaks. The kernel's stack stays,
serving container networks and native sockets, until it is answered; the
parts of the deletion that do not touch containers go ahead.

**Where it bites:** `kernel/src/net/veth.rs`, `bridge.rs`, `nat.rs`,
`kernel/src/cnetwork.rs`, `kernel/src/netns.rs`, `kernel/src/container.rs`;
the daemon is `services/netstack/src/main.rs`.
