## A-Q26 — [A] When you answer a program's permission prompt with "Always allow", what should "always" mean? — Status: OPEN

**In short:** a program can now ask you for extra access ("Photos wants to
read your camera's port", "Clock wants to set the time"), and the desktop's
prompt answers Allow or Deny. Lane C's prompt also has an "Always allow"
checkbox, and nothing yet says what it does. Today an Allow lasts until the
program closes; the next time it starts, it asks again. Should "Always allow"
make the answer outlive that, and for how long?

**Terms, glossed:**
- *capability*: a permission token held over one specific thing (a process,
  a port, the clock); holding it is what lets a program do the thing.
- *the program's fingerprint*: a checksum of the program file's contents --
  the same file gives the same fingerprint; an update or a tampered copy
  gives a different one.
- *revoke*: take a granted permission back.

| option | *What changes:* | for | against |
|---|---|---|---|
| **A. No "Always"** | the checkbox goes; a program asks again every time it starts | nothing to build or to forget about; every grant is visible when made | a program that needs the access daily asks daily |
| **B. Remember it for that program, by fingerprint** (recommended) | the program gets the access at every later start without asking; Settings lists what you allowed, to revoke; an updated program asks again | design.txt's own model -- "Users can set capabilities on individual apps", asked "when they install or when they run" -- and the checkbox is the quick way to set one | the most to build: a store, the grant made at each start, a Settings page (lane C) |
| C. Remember it until you log out or restart | no prompt for the same program and the same access until then | no store on disk; fewer prompts in a session | forgotten silently at restart, which looks like a bug; a long session accumulates grants nobody reviews |
| D. Remember it for that program, by name or path | as B, but the program is recognised by where it is, not by what it is | simpler than a fingerprint | any program placed at that path inherits the access -- a replaced or tampered program gets it too |

**My recommendation: B.** It is the persistent per-program grant design.txt
describes, and "Always allow" is just the prompt's way to make one; the
fingerprint means a program that changes must ask again, which D cannot
promise. A is a fine stopgap if B waits.

**Where it bites:** `kernel/src/cap/request.rs` (an approval lasts as long as
the process); lane C's `gui/desktop/src/security_dialog.rs` (the checkbox);
design-decisions 1548.

**If this is never answered:** nothing unsafe. An Allow lasts until the
program closes, and the checkbox should be hidden or do nothing; programs
that need the access ask again each time they start.
