## A-Q31 — [A] Which WiFi network should the test PC join, and how should its password reach it? — Status: OPEN (raised 2026-10-30)

**In short:** SlateOS's WiFi driver (Linux's own mt7925e, decision 1593)
now joins password-protected networks in simulation. The next step is the
test PC's real card joining a real network, which needs that network's
name and password. You are asked two things: which network -- your home
network, or a separate test one -- and how the password should get to the
test PC, where SlateOS boots from the E: drive.

**Terms.** *WPA2* / *WPA3*: the password-protected kinds of WiFi network;
SlateOS joins WPA2 only, so far. *Boot medium*: the files SlateOS starts
from, which `scripts/pikvm.py` writes to the test PC's E: drive. *Kernel
command line*: settings handed to SlateOS as it boots, printed in its
startup log.

**Which network**

| Option | *What changes:* |
|---|---|
| A. Your home network | Nothing to set up. Its password is stored on this PC and on the test PC's E: drive, readable by anyone with those. |
| **B. A separate test network** (a phone hotspot, or a spare router), WPA2 | A password that guards nothing else; it can sit in a test file without care. Needs the hotspot or router on while the test runs. |

If the network you choose uses WPA3 *only*, SlateOS cannot join it yet
(that is its own piece of work); WPA2, or WPA2/WPA3 "mixed" mode, is fine.

**How the password gets there**

| Option | *What changes:* |
|---|---|
| **1. A file on the boot medium** | You put the name and password in a file on this PC outside the repository (say `C:\Users\Computer\.slateos-wifi`); `pikvm.py` copies it to the E: drive, and the WiFi driver reads it there. Never in a log, never in git. |
| 2. The kernel command line | Simplest to build, but the password is printed in every startup log and the boot test's records. |

- My recommendation: **B and 1** -- a test network, its password in a file
  that never reaches git or a log. With A, still 1.
- If this is never answered: nothing breaks. The simulated tests keep
  running on every boot; only the real card's join waits. Its scan does
  not need an answer, only the PiKVM back on the network.
