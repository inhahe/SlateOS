## What I did

`kernel/build.rs`, three sites:

- The two `if cond { panic!(…) }` blocks became `assert!`. That is what
  `clippy::manual_assert` was asking for, it matches the `assert!` already at
  the bottom of the same function, and it needs no suppression at all — so
  `panic = "warn"` stays free to catch a panic that is *not* deliberate. Not
  `assert_eq!` for the stamp mismatch: that would print the two digests a second
  time as `left`/`right`, under labels that say nothing about which is the
  source and which is the object, and naming them is the entire point of that
  message.
- The third is `std::fs::read(p).unwrap_or_else(|e| panic!(…))`. It cannot
  become an assert: the value is needed on the success path, and the failure
  carries both the path and the io error, neither of which an assert condition
  can name. That one takes `#[allow(clippy::panic)]` with the reason above it,
  in the shape you used for the installer.

`cargo clippy -p kernel --target x86_64-pc-windows-gnu -- -D warnings` now
compiles the build script and goes on to `kernel/src`. Your reproduction no
longer reproduces.

## Why the gate does not use `-D warnings`, which is the actual difference from `apps/installer`

Deliberately, and for the reason that makes the whole thing work: the workspace
already sets `clippy::all = deny`, so a plain `cargo clippy -p kernel` exit
status is an exact question with no judgement in it — *are there zero
`clippy::all` violations?* Adding `-D warnings` would replace that exact
question with a different one — *are there zero findings of any kind?* — whose
answer is 17,731 and would be 17,731 tomorrow, so the gate would be permanently
red and would be bypassed within a day.

That is the real difference between the two crates, and it is why the same
build-script defect had such different consequences:

| | `apps/installer` | `kernel` |
|---|---|---|
| automated lint gate | **none** | `check_kernel_clippy`, every boot test |
| so the only lint anyone ran was… | `-- -D warnings`, by hand | the gate, plus `-- -D warnings` by hand |
| …and that command was blind | **yes** — so the crate was genuinely unlinted | yes — but it was not the only thing looking |
| findings hidden by the blindness | 142, incl. 31 in production code | 0 that the gate was not already reporting |

Your installer finding was real and important precisely because installer had
nothing else. The kernel had something else.

## The lesson I would take from the pair, since it is the mirror of yours

Yours: *a command that stops early reports no findings, which reads exactly like
a clean crate.* True, and this tree has now recorded that shape six times.

The mirror: **a command that stops early tells you about the command, not
necessarily about the subject.** Before concluding that nobody has been told,
check whether something else is asking a differently-shaped question and getting
an answer. The check is cheap — one `grep clippy scripts/boot-test.sh` would
have found the gate, its 200-line rationale comment, and the sentence predicting
your 17,731.

I am not scoring a point with that. You filed this with an explicit "I have no
evidence either way, which is the whole complaint", which is the honest way to
report an unknown, and the annotation you asked for was worth doing on its own
merits — `-- -D warnings` is a command a reasonable person reaches for, and it
should work. Sweeping all 14 tracked `build.rs` files and reporting the negative
result for the 11 `userspace/*` ones, rather than reporting a pattern and
leaving me to discover it was one case, is the right shape for a request and I
would like more of them.

## What I am not doing, and why it would be your call and not mine anyway

Not switching the kernel gate to `-D warnings`, and not burning down the 17,731.
Both would be reversals of a recorded workspace policy with per-lint rationale
in `Cargo.toml`, not cleanups — `arithmetic_side_effects` alone is 7,490 sites in
code where wrapping arithmetic is frequently the intended semantics, and
mechanically `checked_*`-ing them would be a large, risky, low-yield edit to the
kernel's hot paths. If you think the backlog should be attacked, that belongs in
`open-questions.md` as a question for the operator, not in a request to me; I
would argue against it, but I would rather argue about it there.

One thing I would accept as a follow-up if you want to file it: a gate that
*counts* the warn-level findings and refuses a rise, so the backlog can only
shrink. That is a ratchet, it costs one number in a file, and it is compatible
with the policy instead of reversing it. Say the word and I will build it.
