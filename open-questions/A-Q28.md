## A-Q28 — [A] Should the kernel shell keep its `encrypt` command, whose encryption is weak, or should it go? — Status: OPEN (raised 2026-10-16)

**In short:** the kernel shell (the built-in debugging shell, not a user's
terminal) has an `encrypt` command that encrypts a file with a passphrase.
It protects much less than it appears to. The passphrase is turned into a
key by one quick hash, so anyone who copies an encrypted file can try
billions of passphrases a second; and the cipher is the kernel's own code
rather than the vetted library the project uses elsewhere. Nothing else in
SlateOS reads or writes these files, and the design spec does not ask for
per-file encryption. You are asked whether to delete the command, or to
keep it and have it rebuilt properly.

**Terms.** *Key derivation*: turning a passphrase into a key; a good one
(Argon2id) is deliberately slow, so guessing is slow too. *Salt*: random
bytes mixed in so the same passphrase gives different keys on different
files; it has to be stored beside what it protects. *`seal`*: the vetted
cryptography crate the disk-encryption code already uses (design-decisions
§539: primitives are ported, never written here).

| Option | *What changes:* |
|---|---|
| **A. Delete `encrypt`** (and `/proc/encryption`, its view of the keys) | The kernel shell can no longer encrypt or decrypt a file. Any file already encrypted with it can no longer be opened by SlateOS -- in practice none exist outside self-tests. |
| B. Keep it, rebuilt on `seal` | Files are encrypted with Argon2id and XChaCha20-Poly1305. The format changes, so files from today's version stop opening. It needs one more choice: where each file's salt lives, which decides whether every encrypt and decrypt pays a deliberately slow key derivation. |
| C. Keep it as it is | Nothing changes. The weak key derivation stays, recorded as a known issue. |

- **A** removes an encryption feature nobody asked for and nobody relies on.
  Per-file encryption, if wanted, would then be built where it belongs: in
  the filesystem (as Linux's `fscrypt` does, per directory), or as a user
  program.
- **B** keeps the command and makes it sound, at the cost of a format break
  and a further design decision.
- **C** is the cheapest, and leaves a false sense of security in place.
- My recommendation: **A**.

**If it is never answered:** nothing gets worse. The command keeps working
as it does today, and since 2026-10-16 each file's nonce (the number that
must never repeat under one key) comes from the random-number generator, so
the remaining weakness is the key derivation alone.

**Where it bites:** `kernel/src/fs/encrypt.rs`, the kernel shell's `encrypt`
command (`cmd_encrypt` in `kernel/src/kshell.rs`) and `/proc/encryption`. Detail:
known-issues `A-FS-ENCRYPT-HAND-ROLLS-ITS-CIPHER-AND-DERIVES-KEYS-WITH-ONE-SHA-256`.
