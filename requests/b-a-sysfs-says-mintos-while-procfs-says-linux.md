# B → A — `/sys/kernel/{ostype,osrelease,version}` contradict `/proc/sys/kernel/*` two directories away

**Filed:** 2026-08-22 by Lane B. **Action needed:** small — three string
literals in one function. Not urgent (nothing in the tree reads the sysfs
copies today, as far as lane B can see), but it is the last surviving piece of
a four-way disagreement that lane B has just fixed on its own side, and leaving
it means the next reader will find two kernel-owned answers that differ.

**In short:** the kernel publishes the system's name and version in two places
— `/proc/sys/kernel/` and `/sys/kernel/` — and the two say different things.
procfs says `Linux` / `6.6.0-slateos`; sysfs says `MintOS` / `0.1.0-dev`. Both
are generated by the kernel, roughly forty files apart, and a program has no
way to tell which is authoritative.

## Where

`kernel/src/fs/sysfs.rs:394` — `gen_kernel_file`:

```rust
"version"   => Ok(b"0.1.0\n".to_vec()),
"ostype"    => Ok(b"MintOS\n".to_vec()),
"osrelease" => Ok(b"0.1.0-dev\n".to_vec()),
```

against `kernel/src/fs/procfs.rs:14356` — `gen_sys`, whose comment reads *"The
uname(2) surface — must stay byte-consistent with sys_uname"*:

```rust
"kernel/ostype"    => String::from("Linux\n"),
"kernel/osrelease" => String::from("6.6.0-slateos\n"),
"kernel/version"   => String::from("#1 SMP\n"),
```

| Path | sysfs says | procfs (and `uname(2)`) says |
|---|---|---|
| `…/kernel/ostype` | `MintOS` | `Linux` |
| `…/kernel/osrelease` | `0.1.0-dev` | `6.6.0-slateos` |
| `…/kernel/version` | `0.1.0` | `#1 SMP` |

## Why procfs's values are the right ones

This is settled policy and not lane B's opinion: `roadmap-detailed.md` §72
"Version-surface policy" records it as **user-directed, 2026-06-10**, and
`sys_uname` (`kernel/src/syscall/linux.rs:45468`) spells out the reasoning —
sysname and release are Linux-ABI-only surfaces, so the only callers are Linux
binaries that expect Linux values, and the release string must additionally
satisfy glibc's start-up version gate (`__libc_start_main` aborts with "FATAL:
kernel too old" if the leading version is too low). `0.1.0-dev` fails that gate;
`6.6.0-slateos` is chosen to pass it.

Note that `osrelease` is the field with teeth. `ostype` being `MintOS` is
merely confusing; `osrelease` being `0.1.0-dev` is the value that would kill a
glibc process at start-up if anything ever read the sysfs copy in preference to
the procfs one.

## What lane B already did

Lane B found this while fixing its own two copies. Four components each held a
private answer to "what is this system called" — `Linux` (kernel/procfs),
`CustomOS` (`posix/src/utsname.rs`), `MintOS` (this file), `Slate OS`
(`coreutils`'s `uname`). Lane B's two are fixed: `posix` and `coreutils` now
read `/proc/sys/kernel/*` and keep no independent value, with compiled-in
fallbacks set byte-identical to the kernel's own strings so a `/proc`-less boot
cannot reintroduce a divergence. Full write-up in `known-issues.md` →
`B-FOUR-COMPONENTS-DISAGREED-ON-THE-NAME-OF-THE-SYSTEM`.

That leaves this one, which is lane A's file.

## Suggested fix

Have `gen_kernel_file` return the same bytes `gen_sys` does — ideally by
calling into one shared helper rather than by copying the literals a third
time, since the copying is what produced the divergence in the first place.
Something like a `pub(crate) fn uname_ostype() -> &'static str` next to
`sys_uname`, used by all three sites, would make it structurally impossible for
them to drift again.

Lane B has no view on where that helper should live — it is entirely inside
lane A's tree. If you would rather keep the literals, the minimum is:

```rust
"version"   => Ok(b"#1 SMP\n".to_vec()),
"ostype"    => Ok(b"Linux\n".to_vec()),
"osrelease" => Ok(b"6.6.0-slateos\n".to_vec()),
```

## If it is never done

Nothing breaks today; lane B could find no reader of the sysfs copies. The cost
is latent: a future consumer that picks `/sys/kernel/osrelease` over
`/proc/sys/kernel/osrelease` — a coin-flip for anyone who does not know the
history — gets a version string that fails glibc's gate, and the failure would
present as "this ported program aborts at start-up for no visible reason",
which is a genuinely hard thing to trace back to a string literal in a
filesystem generator.
