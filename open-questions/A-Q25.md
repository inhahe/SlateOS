## A-Q25 — [A] Should a debugger be able to take over a program that is already running, and who decides? — Status: OPEN

**In short:** a debugger (GDB, LLDB) can now debug any program it starts
itself, its threads and child programs included. It cannot take over a
program that is *already running* -- `gdb -p 1234`, `strace -p 1234`, or a
crash window's "debug this program" -- because that program never agreed to
it, and your rule (design-decisions §24) is that the right to look inside
another program comes from a token held over that program, never from simply
being the same user. Something has to hand out that token, and nothing does
yet. Who should?

**Terms, glossed:**
- *attach* (`PTRACE_ATTACH`, `PTRACE_SEIZE`): take control of a running
  program from outside -- stop it, read and change its memory and registers.
- *the token* (`DEBUG` right): a capability held over one specific program;
  holding it is what lets a debugger do all of the above.
- *descendant*: a program this one started, or one those started, and so on.
- *Yama*: the policy most Linux desktops ship, under which a program may
  attach only to its own descendants unless an administrator lets it.

| option | *What changes:* | for | against |
|---|---|---|---|
| **A. Ask the user** (recommended) | `gdb -p 1234` shows "Allow gdb to inspect firefox?"; yes gives gdb the token for that program only | the user is the authority, as §24 intends; works for any program | needs a prompt in the desktop (lane C) and in a text terminal |
| B. The program may agree in advance | a program can name who may attach to it (Linux's `prctl(PR_SET_PTRACER)`, which crash handlers use); nobody else can | no prompt; the target consents | only programs written to do so; `gdb -p` on anything else still refused |
| C. A debugger may attach to its own descendants | as Yama: what the debugger's own children started can be attached to | no prompt | `gdb -p` on a program from another terminal is still refused, as on Ubuntu without `sudo` |
| D. Administrators may attach to anything | `sudo gdb -p 1234` works | simple | routine debugging needs administrator rights |
| E. Same user may attach to anything | `gdb -p` works on all your own programs | what classic Unix does | exactly the "same user" authority §24 rules out: one compromised program can read every other one's memory, passwords included |

**My recommendation: A, with B alongside** (a program's own advance consent
needs no prompt). A keeps the decision with the person §24 trusts, and B covers
crash handlers without one; D could be added later for administrators.

**Where it bites:** `kernel/src/proc/ptrace.rs` (`PTRACE_ATTACH` and
`PTRACE_SEIZE` answer `EPERM`); lane D's `requests/d-a-a-debugger-needs-ptrace-
for-native-programs.md`; `known-issues/A-ptrace-tier-2-*.md`. Everything else a
debugger needs is built: an attached program would be handled as a started one
is.

**If this is never answered:** nothing gets worse. Debugging a program the
debugger starts (`gdb ./prog`, `strace ./prog`, an IDE's "run under
debugger") works fully; only taking over an already-running program is
refused, as it is today.
