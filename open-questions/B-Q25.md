## B-Q25 — [B] When the original program never notices that its output could not be written, should ours copy that silence or report it? — Status: OPEN (raised 2026-10-07)

**In short:** most of SlateOS's command-line tools are faithful copies of
GNU programs, measured against the originals. When one of them cannot write
its output -- the disk is full, or its output was closed -- the GNU
*coreutils* programs (`ls`, `cat`, `sort`...) say `write error` and exit with
a failure status, and ours do the same. But a few GNU programs from other
packages never check at all: they exit with success and say nothing, and
the output is simply gone. `which` and `ed` are two (`which ls > out` on a
full disk leaves `out` empty and reports success). Should our copies of
those programs copy the silence, or report the failure as the coreutils
programs do?

**Where it stands today -- inconsistently:**

| program | upstream (measured) | ours now |
|---|---|---|
| `which` (GNU which 2.21) | silent, status 0 | reports `write error`, status 1 -- recorded as a deliberate difference |
| `ed` (GNU ed 1.20.1) | silent, status 0 | reports `write error`, status 1, on a full disk -- never recorded as a choice |
| `hostname` (Debian 3.23) | silent, status 0 | silent, matching |
| `patch` (GNU patch 2.7.6) | silent, status 0 -- and with its output *closed* it writes its `patching file f` line into `f` itself, the file it was patching (measured) | silent, matching; never writes into `f` (its files cannot take the closed descriptor -- `TD-B-GUARDED-PROGRAMS-OPEN-FILES-WITHOUT-OPEN-SAFER`), which is not part of this question: copying a corruption is not on the table |

| Option | *What changes* | For | Against |
|---|---|---|---|
| **A. Report it, in all four** *(recommended)* | `hostname > out` and `patch -o - ... > out` on a full disk say `write error` and fail, as `which` and `ed` already do | a script that saves a program's answer to a file is told when the answer was lost, instead of carrying on with an empty file; matches every coreutils program, so one rule covers the whole toolset | differs from those four originals in a case their users rarely meet; a script that *relied* on the success status in that case would now see a failure |
| B. Copy the silence, in all four | `which` and `ed` stop reporting; output that could not be written is lost with a success status, as upstream | exact fidelity, which is how every other behaviour of these programs is decided | keeps a known way to lose output without any sign, on purpose |
| C. Leave it as it is | nothing | no work | `which`/`ed` and `hostname`/`patch` answer the same situation in opposite ways for no stated reason |

**Words used above:**
- *write error*: the program tried to print its output and the system
  refused (the disk was full, or the output had been closed).
- *status*: the number a program ends with -- 0 for success -- which
  scripts test to decide what happened.

**If it is never answered:** nothing breaks and nothing is blocked; the
four stay as the table says. The cost is the inconsistency, and that the
next program ported from outside coreutils has no rule to follow.

**Where it would change:** `userspace/coreutils/src/bin/{which,ed,patch}.rs`
and `.../hostname/main.rs` -- each ends through `stdfd::close_stdout` or
does not -- and their `scripts/*-diff.sh` cases, which would carry the
choice as an expected difference. Found while adding the descriptor guard
to `ed`, whose harness had never measured a full or closed output.
