## F-Q13 — How should you be able to tell a real system password prompt from a program's fake? — OPEN

**In short:** the password manager asks for its master password in a window
of its own, and any program can open a window that looks exactly like it and
collect the password itself -- a window's contents and title are whatever its
program draws. Only the system can show you something a program cannot fake.
There are three ways, each with a cost: a mark only the system can draw
(cheap, but you have to notice it is missing), a key you press before typing
a password that no program can intercept (like Ctrl+Alt+Del on Windows: a
fake can never receive what you type after it, but it is one more key), or
dimming and freezing the rest of the screen while a real prompt is up (as
Windows does for its permission prompts: distinctive, but a fake can copy the
look). The question is which to build.

**Today:** nothing tells them apart (`known-issues/C-THE-PASSWORD-PROMPT-CAN-BE-IMITATED-BY-ANY-WINDOW.md`).
Whichever is chosen also waits on the C library giving native programs the
channel connection that lets the compositor know which program owns a window
(`requests/f-d-the-c-library-s-slateos-channel-calls.md`): until then the
compositor cannot vouch for the password manager either.

**Options.**

- **A. A mark only the system can draw.** While a real prompt has the
  keyboard, the taskbar -- which no program can cover or draw into -- shows a
  lock and the true name of the program asking.
  *What changes:* a lock appears on the taskbar beside real prompts; a fake
  shows none, or shows its own program's name.
  For: no extra step. Against: protects only someone who notices the lock is
  missing, which studies of browser padlocks say most people do not; and a
  fake that goes full screen hides the taskbar unless full screen is made to
  give way to prompts.
- **B. A secure key before any password** (the system's equivalent of
  Ctrl+Alt+Del). A real password prompt does not take typing until you press
  a key combination that only the system ever receives -- no program can
  see it or fake it. Pressed with a fake on screen, it tells you no system
  prompt is waiting.
  *What changes:* typing the master password becomes "press the key, then
  type"; a fake prompt never receives the password of anyone who keeps to it.
  For: the one defence that does not rely on noticing anything; Windows used
  it for sign-in for twenty years. Against: one more key, every time; and it
  protects only people who learn the habit.
- **C. Both A and B** (recommended).
  *What changes:* the lock on the taskbar, and the key before typing.
  For: the key is the protection, the lock is what teaches it ("real prompts
  show this, and want this key"). Against: the costs of both.
- **D. A secure desktop**: the rest of the screen dims and stops responding
  while a real prompt is up.
  *What changes:* real prompts take over the screen until answered.
  For: unmistakable, and nothing else can be clicked meanwhile. Against: a
  fake can copy the look, so it protects little against imitation on its own;
  it can be added to any of the above later.

**Recommendation:** C.

**If this is never answered:** nothing is built, and a program can imitate
the prompt as it can today. Nothing else is blocked.

**Where it bites:** lane C's prompts (`gui/credentialsd`,
`gui/desktop/src/security_dialog.rs`) and the compositor's key grabs and
window list (`gui/compositor`); `requests/c-f-let-the-user-tell-the-systems-own-prompts-from-a-programs.md`.
