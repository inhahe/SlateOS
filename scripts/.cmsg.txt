apps/dictionary: a failed open says so, instead of looking like an empty file

Lane A's gate 52 turned main red: file_status is written in production
and read by nothing. It is the third of three in this lane today, and
the third where the dead field was a missing feature rather than
leftover code -- jsonviewer's last_open was a truncation warning nobody
drew, renamer's raw_name was the un-lossy name the rename should have
used. os-14's "check before baselining" prior is now three for three.

file_status holds the outcome of the last open or save, including
"Could not read /path: <err>". Nothing read it. So a failed open closed
the picker, left the lists unchanged, and said nothing -- which is
exactly what a file that loaded and happened to be empty looks like.
The user's next move is to wonder where their favourites went.

status() now returns it when set, in preference to the search hint: a
hint is always true and this is news. handle_key clears it on the next
keystroke, so it does not report an open from five minutes ago as though
it were now, which would be its own small false claim.

Two tests. The first asserts the failure is DRAWN, not that the field
holds it -- via the existing `shows` helper, because a field that was
assigned proves nothing a user would see. It opens with a control: the
fixture must actually fail to read, or the test is about nothing. The
second pins the clearing, with a control that clearing does not leave
the status line empty.
