## F-Q12 — Should a newly opened window be stopped from taking the keyboard unless the user's own action asked for it? — OPEN

**In short:** when a program opens a window, the window takes the keyboard,
so whatever you type next goes to it. That is what you want when you have
just started the program -- and wrong when a program you are not using opens
a window while you are typing a password somewhere else: the rest of the
password goes to it. SlateOS now lets a launcher (the start menu, a file
manager) hand the program it starts a one-time token saying "the user asked
for this", and a window opened with that token always gets the keyboard. The
question is what happens to a window opened *without* one: let it take the
keyboard anyway, as GNOME and KDE do today, or keep it in the background with
its taskbar button flashing until you click it, as both are moving towards.

**What is already decided** (design-decisions 1386, autonomous, reversible):
a program can no longer take the keyboard by "restoring" a window it already
had -- the easy way in until now -- and a program you started and then left
(you went on typing elsewhere while it loaded) opens in the background. Only
new windows with no token at all are still let through.

**The catch with refusing them:** a terminal cannot hand on a token. The
shell running inside it was started long before you typed the command, so
the token would have to be one from that moment, which is not one of your
actions any more. Under the strict rule, every program you start by typing
its name in a terminal opens behind the terminal, with its taskbar button
flashing -- GNOME's "is ready" notification is the same thing, and the most
common complaint about GNOME's strict setting.

**Options.**

- **A. Keep letting new windows in** (today; GNOME's and KDE's default).
  *What changes:* nothing.
  For: no program opens in the background unexpectedly.
  Against: a program can still take your keys at a moment it picks, by
  opening a new window (a small or invisible one would do) -- once per
  window, each one seen as it opens.
- **B. Refuse them once the launchers hand tokens on, and make terminals
  work another way first** (recommended).
  *What changes:* after the start menu, the file manager and the other
  launchers pass tokens on (requests sent to lanes C and E today), and once
  the compositor can tell that a program was started from the terminal you
  are typing in (it needs to see which process connected, which native
  programs cannot show it until the C library's channel calls exist), a
  window opened with no token waits in the background. Nothing changes until
  then.
  For: closes the last way for a program to take your keys uninvited,
  without making terminal use worse.
  Against: the terminal part waits on other work (lane D's channel calls,
  and a way to ask the kernel which process started which).
- **C. Refuse them as soon as the launchers hand tokens on, terminals or
  not.**
  *What changes:* programs started from a terminal open behind it, taskbar
  button flashing, until you click them.
  For: the protection sooner.
  Against: the GNOME complaint above, for everyone who uses a terminal.

**Recommendation:** B.

**If this is never answered:** SlateOS stays at A. Nothing is blocked, and
nothing gets worse with time: the hole A leaves open is the one GNOME and
KDE leave open by default today.

**Where it bites:** `gui/compositor/src/activation.rs` (`NewWindows`, the
policy -- one call switches it); design-decisions §1386.
