## A-Q24 — [A] Should programs be able to change a file by writing to a memory mapping of it? You declined it in June; lane D reports SQLite's WAL mode and LMDB need it. — Status: OPEN

**In short:** a program can ask for a file to appear in its memory, so that
reading memory reads the file. It can also ask that *writing* that memory
change the file, and that every other program with the same file mapped see
the change. SlateOS refuses the second kind. You decided that in June
(design-decisions §22, narrowed by §23: "won't fix"). Lane D now reports what
it costs: SQLite's faster journal mode (WAL) needs it for a small shared file,
the LMDB database needs it, and so does any program that edits a file through
a mapping. Do you want it built, or kept refused?

**Terms, glossed:**
- *mapping* (`mmap`): a file shown in a program's memory, read from the disk
  a page at a time as the program touches it.
- *shared writable mapping* (`MAP_SHARED` with write access): one whose
  writes go to the file, and which every other program mapping the file sees.
  The other kind, a *private* mapping, keeps its writes to itself; that kind
  works today, natively and for Linux programs.
- *write-back*: copying the changed pages to the disk -- when the program asks
  (`msync`), when it unmaps, or from time to time.
- *page cache*: one copy of each file page in memory, shared by everyone who
  has the file open or mapped. The read-only half of this exists since §23;
  the write half does not.

| option | *What changes:* | for | against |
|---|---|---|---|
| **A. Build it** (recommended) | SQLite in WAL mode, LMDB and programs that edit files through mappings work, natively and as Linux programs | it is what real software expects of an OS; the shared read-only page cache §23 asked for is already the base it needs | the largest piece of memory-management work left: tracking which pages changed, writing them back, and keeping `read`/`write` and every mapping of a file in agreement, through truncation and crashes |
| B. Only for files kept in memory (`/tmp`) | the same, for files under `/tmp` only; elsewhere still refused | no disk write-back to build | SQLite keeps its shared file beside the database, not in `/tmp`, so neither SQLite nor LMDB is helped |
| C. Keep refusing (today) | nothing | no new machinery | SQLite must use its slower journal mode; LMDB and mapping-based editors do not run |

**My recommendation: A.** The refusal was reasonable when nothing ran that
needed it; programs that do are arriving now (lane D's C library already
turns this refusal into an error, and lists SQLite and LMDB as broken by it).
The read-only shared page cache (§23) built since is most of the foundation:
what is missing is marking pages as changed, writing them back, and making a
`write` to the file and a write through any mapping the same change.

**Where it bites:** `kernel/src/syscall/linux.rs` `linux_file_mmap` (a
writable `MAP_SHARED` is `ENOSYS`), the same for the native `SYS_MMAP_FILE`
(lane D's `requests/d-a-a-native-program-cannot-map-a-file.md`);
`kernel/src/mm/page_cache.rs`; `known-issues/TD22.md` records the decision.

**If this is never answered:** nothing gets worse. Writable shared mappings
stay refused with an error, as today; SQLite runs in its rollback-journal mode
(slower, correct); LMDB and programs that edit files through mappings do not
run. Nothing else waits on this.
