## C-Q35 — [C] Tools can read and press a program's controls only from inside that program. Should lane C build the channel that lets another program -- a screen reader, a test script -- do it, and how does such a program get permission? — Status: OPEN (raised 2026-10-06)

**In short:** every window built with the desktop's toolkit can now
describe itself control by control -- each button, field, list and menu,
what it says, whether it is on -- and do what is asked of it exactly as a
click would. But only from inside the program that owns the window: no
other program can ask yet. So a screen reader, a macro recorder or an
automated test still cannot reach any program but itself. The design
describes the missing piece (an "automation channel") and the
permissions it needs, but no lane has it on its list. The choice is
whether lane C builds it now, and how a program earns the right to read
and press another program's controls.

**Question.**

1. **Who and when.** The *automation channel* (a connection one program
   opens to another to ask about its controls) needs: a library every
   program links (it answers on the program's behalf -- `libautomation`
   in the design), the `automate` command (lists programs, prints a
   window's controls, presses one), and later two words in the shell
   (`on`, to run something when a program reports an event; `invoke`, to
   press). The library and the command sit naturally in lane C's part of
   the tree, beside the toolkit that already does the in-program half; the
   shell's words are lane B's.
2. **Permission.** The design names two rights: `automation.ui_inspect`
   (read another program's controls) and `automation.ui_control` (press
   them). A password field's text is never readable, whatever the rights --
   that is already so. What decides who holds the rights?

**Options for permission.**

| | How a tool gets the rights | For | Against |
|---|---|---|---|
| **A. At install** | The tool's package lists the rights; the person installing it approves them, and a Settings page can take them away. | A screen reader works the moment it is installed, with no prompt the blind user must first find. | Every installed tool that asked can read every window from then on, unnoticed. |
| **B. Asked at first use** | The first time a tool reaches into a program, the person is asked -- "*Reader* wants to read and press the controls of *Mail*": once, always, or no -- as the password service already asks (§1417, §1464). | Nothing is read until someone says yes, about that program; a "no" is remembered. | A prompt per program; a screen reader would need the "always, for every program" answer offered, which is A by another road. |
| **C. Only the system's own tools** | Only programs shipped and signed with the system hold the rights. | The smallest surface: no third-party program can read anyone's screen. | Third-party assistive tools -- voice control, switch access, an alternative screen reader -- cannot exist. |

*What changes:*
- **A:** an installed screen reader reads every window at once; a tool installed for one job can read every other program too.
- **B:** a tool's first look at each program shows a prompt; until someone answers yes, it sees nothing.
- **C:** only the system's own screen reader and test tools can read or press another program's controls.

**If never answered:** safe -- today no program can read or press
another's controls at all. Blocked: any screen reader, macro recorder or
cross-program test.

**Claude's recommendation:** lane C builds the library and the `automate`
command now, in `gui/`; permission by **B**, with the prompt offering
"always, for every program" for assistive tools that need it, and a
Settings page (lane E's) to see and take back what was granted. Meanwhile
lane C will build what holds under every option -- the messages a
program answers with (its window's controls, a search over them, an
action and its refusal) and the part of a program that answers them --
tested inside one program, with the permission check left as the one
hook the answer fills in.

**Where it bites:** `gui/toolkit/src/widget/automation.rs` (the tree and
its actions, done) and every component's `Accessible`; a new crate in
`gui/` for the channel; the kernel's check that a caller holds a
service's key (`design-decisions.md` §1518), which the password service
already uses; lane B's shell for `on` and `invoke`; `roadmap-detailed.md`
§4.13.
