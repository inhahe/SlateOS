## A-Q27 — [A] Should a program be given "run on these cores" and "use the Gaming tuning while this runs", remembered, as Process Lasso does on Windows? — Status: OPEN (raised 2026-10-09)

**In short:** you asked (2026-10-09, in chat) whether SlateOS needs controls
like Process Lasso's -- a Windows tool that keeps rules per program: its
priority, which processor cores it may use, a limit on its share of the
processor, a power plan while it runs. Most of what Process Lasso does exists
because Windows lets a busy background program make the whole desktop
sluggish; SlateOS's plan fixes that in the system itself, by keeping a share
of the processor, memory and disk for the desktop and the program you are
using. Three per-program settings are already planned. Two that are not:
which cores a program runs on, and switching the system's tuning while a
program runs. Should those two be added -- or more?

**Terms, once each.** *Core*: one of the processor's independent units. Recent
Intel processors mix fast "performance" cores with slower "efficiency" ones,
and some AMD processors have two groups of cores of which only one has the
extra cache games run faster with. *Workload profile*: SlateOS's named presets
for the scheduler and memory settings -- Desktop, Database, Development,
Gaming (`design.txt`), chosen today by hand.

**What exists or is planned**, against Process Lasso's features:

| Process Lasso | SlateOS |
|---|---|
| ProBalance: lowers a busy program's priority while the desktop needs the processor | planned, as a guarantee instead of a reaction: processor time, memory and disk bandwidth kept for the desktop and the program in front (roadmap-detailed, "Guaranteed Resource Headroom"); built: a program waiting on input gets a small priority boost |
| A remembered priority per program, processor and disk | planned: "A default priority per program, remembered" (your proposal of 2026-09-26) |
| A cap on a program's share of the processor | planned: `resource.cpu`, a limit as a percentage or a time |
| Disk priority | built: a disk scheduler with priority classes (BFQ's design); the real-time class only with a permission |
| Which cores a program may use, remembered | **not planned.** Possible per launch today (`taskset`, `SYS_SCHED_SET_AFFINITY`); nothing remembers it, and the scheduler does not know which cores are fast and which slow |
| A power plan or "performance mode" while a program runs | **not planned**: the profiles exist, switched by hand |
| Rules: "if this program does X for Y seconds, do Z" | partly: the stall and thrash watchdogs (roadmap-detailed §6.12) find and report; nothing acts per program |
| Limit on how many copies run; restart when it exits | for services only (the service manager restarts them) |

| Option | *What changes:* |
|---|---|
| **A. Add the two missing settings** (recommended) | In the task manager and Settings a program can be given "run on these cores" (or simply "fast cores" / "efficiency cores") and "use this profile while it runs"; both remembered, applied at every start, kept with its remembered priority. The scheduler learns which cores are which. |
| **B. Only what is planned** | The reservations and the three planned settings. A game that runs better on the fast cores, or wants the Gaming profile, needs it set by hand each time. |
| **C. A full rule engine** | A, plus rules you write: "if this program uses more than N% for T seconds, lower it / cap it / tell me". The most to build and to explain. |

**For A.** Which cores suit a program is something the system cannot always
guess: on processors with two kinds of cores, or two groups of them, a game,
an old program, or a background job each has a right answer the user knows
and the scheduler does not. It is the main reason Process Lasso is used on
current hardware, and Windows itself grew "Game Mode" for the same need.
Switching the profile while a game runs is the rule a user would otherwise
apply by hand each time. Both fit the remembered-priority setting already
planned: one place per program, one precedence order.
**Against C, for now:** a rule engine mostly repairs what the reservations are
built to prevent. If the reservations turn out not to be enough, it can come
later; the trigger would be the stall watchdogs reporting stalls the
reservations did not stop.

**If never answered:** nothing breaks or gets worse. The planned settings are
built anyway; cores can still be chosen per launch (`taskset`), only not
remembered.

**Claude's recommendation:** **A.** Meanwhile lane A builds nothing for it.

**Where it bites:** the kernel scheduler (`kernel/src/sched/`, affinity masks;
core types from the processor's identification data) -- lane A; the store of
per-program rules, shared with the remembered priority (roadmap-detailed §1.3,
"A default priority per program, remembered"); the task manager (lane E) and
Settings (lane C).
